# Company Operating System — bootstrap

One mono-repo that gives an AI agent whole-company context to run go-to-market,
product, and ops for your business. Run in order: paste PHASE 1 into your coding
agent in an empty repo; once the scaffold exists, paste PHASE 2 in the same repo.

Both phases: for EVERY question, "not decided yet" is valid — write `# TODO: <decision
needed>` in place of real content and NEVER invent an answer. Each phase ends by
listing every open `# TODO:`.

---

## PHASE 1 — interview + scaffold

You are helping me build a "Company Operating System": one mono-repo that gives an
AI agent whole-company context so it can run go-to-market, product, and ops work
for my business. The CURRENT directory is that repo. Create everything as top-level
dirs here. Do NOT create a wrapper folder.

STEP 1 - INTERVIEW ME. Ask one question at a time. Cover:
- Business: what we sell, to whom, the core problem.
- Customers: ICP(s), buyer personas, competitors.
- Operating model: revenue channels, pricing, sales motion, recurring workflows.
- Assets: product code, website, CRM, decks, existing content (get repo URLs if any).
- Data sources: email, calendar, CRM, call transcripts, billing, analytics, social -
  name the exact tools and which are wired up as MCPs vs not.
- Team + cadence: who does what, recurring jobs to automate.

For EVERY question, "not decided yet" is a valid answer. When I pick it, write
`# TODO: <decision needed>` in place of real content. Never invent an answer.

STEP 2 - SCAFFOLD. Create only the dirs my answers justify; skip the rest.
- customer/    company facts: icp, personas, competitors, pricing (single source of truth)
- product/     product code as git submodule IF a repo exists; else stub + `# TODO: repo URL`
- websites/    marketing site + blog, same submodule rule
- gtm/         go-to-market; name subdirs after MY actual channels, not a template
- decks/       pitch/sales decks by audience
- cronjob/     one dir per recurring UNATTENDED job, each with a SPEC.md
- context/live/       auto-generated by jobs; never hand-edit
- context/over_time/  append-only, timestamped filenames, never edit in place
- context/stable/     curated long-lived docs, incl. team.md and open-decisions.md
- config/      ONLY if I have cross-cutting config; otherwise skip, secrets go in root .env
- tools/       internal apps/scripts, only if any exist

STEP 3 - WRITE CLAUDE.md (root). Dense, for an agent not a human. Sections: one-line
company description; the mono-repo idea; layering / where-things-go rules; key file
anchors; my conventions; and a MCP / data-source table (source -> connected? or TODO).
Add a nested CLAUDE.md inside any subtree with its own rules. Put path-scoped write
rules in `.claude/rules/<name>.md` (YAML frontmatter with `globs:`). Put on-demand,
interactive playbooks in `.claude/skills/<name>/SKILL.md`.

A recurring job goes in cronjob/ (unattended) OR as a skill (I trigger it), never both -
cross-reference if related. Park undecided strategic questions in
context/stable/open-decisions.md; park team/cadence in context/stable/team.md.

RULES:
- Fill everything from my answers; unknowns stay `# TODO:`.
- Fewest words that fully land the point.
- End by listing every `# TODO:` so I see what is still open.

Start the interview now with the first question.

## PHASE 2 — wire the machinery

Run this only after PHASE 1 has scaffolded the repo (CLAUDE.md at root, customer/
product/ websites/ gtm/ decks/ cronjob/ context/ and .claude/ dirs).

You are wiring up the MACHINERY for a "Company Operating System" mono-repo that a
previous session already scaffolded. Run in the repo root. Everything you do MUST be
idempotent - safe to re-run, never duplicating a hook, target, or symlink. Read the
existing CLAUDE.md and dir tree first; do not undo prior work.

STEP 1 - ASK ME (one at a time, "not decided yet" -> leave a `# TODO:`, never invent):
- For each stubbed submodule (product/, websites/, any other), the git repo URL.
- Do my product/website submodules need a private-access token in cloud/CI? (y/n)
- Which CI host: GitHub Actions (default), or other?
- Any hard house rules to enforce mechanically (max file length, banned chars in
  CLAUDE.md, "secrets only in .env", context/ write discipline)?

STEP 2 - SUBMODULES. For every URL I gave, replace the stub dir with a real submodule
(`git submodule add <url> <path>`). Leave stubs with an unresolved `# TODO: repo URL`
untouched. If any submodule needs a token, write scripts/setup_cloud_env.sh that
injects it from an env var before `git submodule update --init --recursive`, and
document the failure mode (missing token -> auth error) in root CLAUDE.md.

STEP 3 - DUAL-TOOL MIRROR. So non-Claude agents (e.g. Codex) read the same context,
write scripts/sync.(sh|py) that idempotently creates a sibling `AGENTS.md` symlink ->
CLAUDE.md next to EVERY non-submodule CLAUDE.md, and prunes dangling ones. CLAUDE.md
stays the single source of truth; never hand-edit an AGENTS.md.

STEP 4 - MAKEFILE. Add (or extend) a Makefile with:
- `make sync`  -> runs the sync script.
- `make ci`    -> runs sync in check-mode (fail if it would change anything) + all
                  Step-1 house-rule validators. Write each validator as a small script
                  in scripts/ (or utils/); a rule I marked `# TODO:` becomes a stub
                  validator that no-ops with a `# TODO:` note.

STEP 5 - HOOKS + CI.
- Pre-commit: add a config (pre-commit or prek) that runs `make ci`. Register it in
  the repo; document the one-time install command in root CLAUDE.md.
- CI: if GitHub Actions, add .github/workflows/ci.yml running `make ci` on push/PR.
- Session-start: add a .claude/ hook that runs `git submodule update --init --recursive`
  (and setup_cloud_env.sh if present) so a fresh session/clone is ready.

STEP 6 - FOLD INTO CLAUDE.md. Add a short "## Build & sync" section to root CLAUDE.md:
the submodule rule, `make sync` after editing shared context, `make ci` before commit,
and the one-time hook-install command. Keep it dense.

RULES:
- Idempotent everywhere; re-running changes nothing on a clean repo.
- Don't fabricate URLs, tokens, or rules I didn't give - those stay `# TODO:`.
- Validate by running `make ci` yourself at the end; report pass/fail.
- End by listing every `# TODO:` and every one-time command I must run manually.
